Lookup-flyten

Endepunktet pattern-matcher den lukkede resultathierarkien.


// WebApi/Program.cs
app.MapGet("/companies/{orgnr}", async (
    string orgnr,
    LookupCompanyHandler handler,
    CancellationToken ct) =>
{
    var result = await handler.HandleAsync(new LookupCompanyQuery(orgnr), ct);

    return result switch
    {
        CompanyLookupResult.Found f        => Results.Ok(f.Response),
        CompanyLookupResult.NotFound       => Results.NotFound(),
        CompanyLookupResult.InvalidInput i => Results.BadRequest(new { error = i.Reason }),
        CompanyLookupResult.Unavailable    => Results.Problem(statusCode: 503),
        _                                  => Results.Problem(statusCode: 500),
    };
});

Hvorfor ikke OpenAPI + Kiota?

Vurdert og bevisst forkastet — for denne skalaen.

Brreg har spec'en

  • OpenAPI: data.brreg.no/81088a24-...
  • Kiota (Microsoft) eller NSwag kan generere strongly-typed klient + alle DTOs fra spec-URLen

Asymmetrien: ~50 endepunkter i spec'en, 2 brukes

TilnærmingLinjer i repoBare det vi bruker?
Kiota default~8000❌ Hele Brreg-API'et
NSwag default~3000❌ Hele Brreg-API'et
Refit (interface)~20✓ Bare det vi skriver
Håndrullet (valgt)~150✓ Bare det vi bruker

Hvor codegen koster mer enn det smaker — her

  • 4000-linjers diff hver gang spec'en regenereres → code review-fatigue
  • IDE-søk treffer 47 endepunkter vi aldri kaller
  • Schema-drift fanges av WireMock-testene uansett (deterministisk, ikke avhengig av regenerering)

"Når ville du byttet?" Når surface vokser forbi ~20 endepunkter, eller når et annet team blir avhengig av Brreg-DTOs. For søsterprosjektet (multi-registry) ville jeg gått Kiota.

Validering — selvvaliderende value object

Validering skjer én gang, på grensen. Etter TryCreate er instansen alltid gyldig.


public readonly record struct OrganizationNumber
{
    private static readonly int[] Mod11Weights = [3, 2, 7, 6, 5, 4, 3, 2];

    public static bool TryCreate(string? raw, out OrganizationNumber result)
    {
        // 1) 9 sifre, 2) starter med 8 eller 9, 3) MOD11
        if (!IsNineDigits(raw)) return Fail(out result);
        if (raw[0] is not ('8' or '9')) return Fail(out result);

        var checkDigit = ComputeMod11CheckDigit(raw);
        if (checkDigit is null) return Fail(out result);              // remainder == 1
        if (raw[8] - '0' != checkDigit.Value) return Fail(out result);

        result = new OrganizationNumber(raw);
        return true;
    }
}

Bonus-gevinst: én færre HTTP-runde for ugyldige innslag. Oppgaven krevde bare 1 + 2; MOD11 er gratis kvalitet.

Caching som dekoratør

HTTP-adapteren vet ingenting om cache. Bytt ut HybridCache uten å røre BrregCompanyProvider.


internal sealed class CachingCompanyProvider(
    BrregCompanyProvider inner,
    HybridCache cache,
    IOptions<BrregOptions> options) : ICompanyProvider
{
    public async Task<CompanyLookupResult> LookupAsync(OrganizationNumber n, CancellationToken ct)
    {
        var cached = await cache.GetOrCreateAsync(
            key:     $"brreg:enhet:{n}",
            factory: async tok => CachedLookup.From(await inner.LookupAsync(n, tok)),
            options: new HybridCacheEntryOptions { Expiration = options.Value.CacheTtl },
            cancellationToken: ct);

        return cached.ToResult();
    }
}

DI-rekkefølgen er eksplisitt: BrregCompanyProvider som konkret klasse, ICompanyProvider → CachingCompanyProvider.

Resiliens via Polly v8

Microsofts anbefalte standardhåndterer gir retry, circuit breaker, rate limiter og timeout.


services
    .AddHttpClient<BrregHttpClient>(client =>
    {
        client.BaseAddress = new Uri(brregOptions.BaseAddress);
        client.Timeout     = brregOptions.RequestTimeout;
    })
    .AddStandardResilienceHandler();   // retry + jitter + breaker + timeout

Mapping mot domenet

  • HTTP 200 → CompanyLookupResult.Found
  • HTTP 404 / 410 → NotFound (410 = slettet fra registeret)
  • HTTP 5xx, timeout → BrregUnavailableException → Unavailable
  • Ekte OperationCanceledException bobler opp — bare timeouts foldes om

Diskriminert union for utfall

Forretningsutfall er ikke exceptions. Lukket hierarki via privat konstruktør tvinger uttømmende switch.


public abstract record CompanyLookupResult
{
    private CompanyLookupResult() { }   // lukker hierarkiet

    public sealed record Found(CompanyResponse Response) : CompanyLookupResult;
    public sealed record NotFound                         : CompanyLookupResult;
    public sealed record InvalidInput(string Reason)      : CompanyLookupResult;
    public sealed record Unavailable                      : CompanyLookupResult;
}

Pattern-match i WebApi gir korrekt HTTP-status: 200, 404, 400, 503 — ingen exceptions som kontrollflyt.

Lokalisering — uten database

Cookie-basert kulturbytte. Ingen sesjonstilstand, ingen JS-interop, ingen DB.


// BlazorWeb/Program.cs
app.UseRequestLocalization(new RequestLocalizationOptions()
    .SetDefaultCulture("en")
    .AddSupportedCultures("en", "nb-NO", "nn-NO")
    .AddSupportedUICultures("en", "nb-NO", "nn-NO"));

app.MapGet("/set-culture", (string culture, string redirectUri, HttpContext ctx) =>
{
    ctx.Response.Cookies.Append(
        CookieRequestCultureProvider.DefaultCookieName,
        CookieRequestCultureProvider.MakeCookieValue(new RequestCulture(culture)));
    return Results.LocalRedirect(redirectUri);
});

Parity-tester sikrer at nb-NO og nn-NO har nøyaktig samme nøkler som standarden — ingen stille engelsk-fallback.

CI/CD — GitHub Actions + OIDC

Ingen secrets lagret i GitHub. Test-gate gjør at røde tester aldri når produksjon.


# .github/workflows/build-and-deploy.yml
jobs:
  build-and-test:                                    # på push, PR, og manual dispatch
    steps: [ checkout, setup-dotnet, restore, build, test ]

  deploy:
    needs: build-and-test                            # ← test-gate
    if: github.event_name == 'push' && github.ref == 'refs/heads/master'
    steps:
      - uses: azure/login@v2                         # OIDC — ingen client-secret
        with: { client-id, tenant-id, subscription-id }
      - run: az acr build ...
      - run: az containerapp update ...

Spørsmål?

Forventede spørsmål

Hvorfor ikke MediatR?

To handlers — eksplisitt DI er enklere å lese. Mediator-mønsteret bærer ikke kostnaden sin på denne skalaen.

Hvorfor sealed som standard?

Lukket for arv, åpent for substitusjon. JIT genererer bedre kode, og det signaliserer intensjon.

Hvorfor MIT-lisens?

Enkelhet for en demonstrasjon — søsterprosjektet bruker AGPL + kommersiell.

Hvorfor norwayeast?

Datasuverenitet og latency for nordiske brukere — Brreg-data er per definisjon norsk.

Hva vil du forbedre?

CachingCompanyProvider mangler en round-trip-test. En eksplisitt MOD11 remainder==1 test ville bevise edge-casen tydeligere.

Hvordan skalerer det?

HybridCache støtter L2 (Redis) bak samme API — én konfigurasjonsendring.
